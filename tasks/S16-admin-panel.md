видалити акаунт).

### 3. Схема (0171) — аудит мусить пережити видалення акаунта
`admin_audit` FK нині блокують `DELETE app_user` (actor_id NOT NULL, target_id RESTRICT).
Право на забуття вимагає видалення, слід аудиту вимагає збереження. Розв'язка:
денормалізувати email у сам запис + послабити FK.
```sql
admin_audit += actor_email TEXT, target_email TEXT   -- знімок на момент дії
actor_id/target_id → ON DELETE SET NULL; actor_id DROP NOT NULL
```
Так слід лишається читабельним («хто кому»), навіть коли акаунта вже нема.

### 5. БЕЗПЕКА
- Видалення — **лише admin**, незворотне: не себе, не останнього активного admin,
  moderator не має доступу взагалі. Аудит із денормалізованим email (див. §3).
- `send-reset` шле лист на ЧУЖУ адресу → rate-limit і аудит (інакше — вектор спаму).
- Ручний verify — аудит (обхід поштової перевірки мусить лишати слід).
- Пошук `q` — лише параметризований ILIKE (жодної конкатенації в SQL).
- Метрики не віддають ПЕРСОНАЛЬНИХ даних (лише агрегати).
- **Веб-панель:** токен у sessionStorage (не localStorage — гине із вкладкою);
  сторінка статична, усе через ті самі гейти; жодних секретів у HTML.
